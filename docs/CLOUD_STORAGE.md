# ОБЛАЧНОЕ ХРАНИЛИЩЕ NODEBASE

## Целевая архитектура

Для Nodebase подходит Supabase: управляемый PostgreSQL + авторизация + Row Level Security. Это будет единая база данных в интернете, а не общий файл и не браузерное хранилище.

- PostgreSQL хранит сущности, связи, доски и размещения.
- Supabase Auth идентифицирует Юрия на каждом устройстве.
- Row Level Security ограничивает доступ данными авторизованного пользователя.
- IndexedDB остаётся локальным кэшем и временным хранилищем для офлайн-режима.
- GitHub Pages публикует только код приложения. Пользовательские данные в GitHub не записываются.

## Почему не просто Google Drive / один JSON

Nodebase — связанная база с параллельными изменениями. Один JSON-файл создаёт конфликты при одновременном редактировании, а Drive не даёт нужных ограничений целостности для сущностей, связей и досок. PostgreSQL подходит для такой структуры лучше.

## Безопасность

- В клиентском приложении разрешено использовать только Supabase Project URL и publishable/anon key.
- Никогда не добавлять service_role key в исходники, GitHub Pages или переменные VITE_*.
- Все таблицы закрыты Row Level Security.
- Каждая строка принадлежит user_id из auth.uid().
- Внешние ключи не позволяют связывать записи разных пользователей.
- Для входа на устройствах используем magic link по электронной почте или пароль.

## Порядок подключения

1. Создать проект Supabase.
2. В SQL Editor выполнить миграцию из файла выше.
3. В Authentication включить Email и выбрать способ входа.
4. Передать в конфигурацию приложения Project URL и publishable/anon key. Service role key не нужен и не должен передаваться.
5. Добавить секреты GitHub Actions: `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`.
6. Подключить Supabase SDK и экран входа.
7. Реализовать первоначальный перенос локальной базы в облако с предварительным просмотром и резервной копией.
8. Переключить репозитории на облачное хранилище; IndexedDB оставить кэшем.
9. Добавить синхронизацию изменений и обработку конфликтов между устройствами.

## Правила первого переноса

Первый вход не должен автоматически затирать облако или локальную базу.

Приложение должно показать:
- количество локальных сущностей, связей, досок и размещений;
- количество записей в облаке;
- варианты «загрузить локальную базу в облако» или «загрузить облачную базу на устройство»;
- создание JSON-резервной копии до переноса.

Если обе стороны уже содержат данные, нужен режим слияния по UUID и явный список конфликтов. Нельзя молча выбирать одну из версий.

## Синхронизация после подключения

- Все записи получают стабильные UUID и user_id.
- Изменения отправляются в PostgreSQL.
- При открытии другого устройства приложение загружает актуальную базу пользователя.
- Для одновременных правок используем updated_at и оптимистическую проверку версии; конфликт показываем пользователю, не теряя данные.
- Удаление сущности, связи или размещения должно быть отдельным подтверждаемым действием.
- Офлайн-изменения складываются в очередь IndexedDB и отправляются при восстановлении сети.

## Текущий статус

Сейчас приложение всё ещё работает через IndexedDB. Облачная схема подготовлена, но облако не подключено, авторизация и синхронизация ещё не реализованы. Для подключения нужен созданный проект Supabase и его публичные параметры.
